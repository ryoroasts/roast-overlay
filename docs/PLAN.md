Phase 1-2 は完成済み。**Phase 3(.klog 実測の重ね)以降を、セッションを分けて進める。**

## なぜ作り直すのか — 位置づけの変化

このツールは当初 **private な検証補助**として作られた。現在は目的が1つ増えている。

> **公開して、Kaffelogic ユーザーに使われることで知名度を作る。**

背景: 焙煎記録(note)は母数が小さく、収益にはならないと確定している
(日本 数百人 / 世界のフォーラム登録 1,244人)。一方
**「記事50本より、使われるツール1個のほうが名前は残る」**という判断で、
kpro-diff の公開を「一回きりのレバレッジ」として位置づけ直した。

→ **private 用の作り(自分だけが分かればよい)から、他人が初見で使える作りへ。**

## いま分かっている課題

### 🔴 A. Level が全プロファイル共通で1つしかない

実測(2026-08-14)。3本読ませて Level=3 固定で表示される。

| プロファイル | 現在の表示 | 推奨Level | 実際に焼いたLevel |
|---|---|---|---|
| Rwanda_Nordic2b | 212.0℃ | 3 | 4.6 / 5.9 |
| Ninja_SlowDev | 226.0℃ | 2.5 | 1.5 |
| Ninja_SlowDev_Light | 226.0℃ | 1 | 1.0 |

補間の計算は正しい。問題は運用と噛み合っていないこと。

**特に致命的**: `Ninja_SlowDev` と `Ninja_SlowDev_Light` は `roast_levels` が同一で、
**Level だけ変えて焼き分けている**(216.5℃ vs 215.0℃)。現状のツールでは
両方 226.0℃ と表示され、**この2本の差が終了温度に出てこない**。実験の肝が見えない。

→ **方針: 推奨Level(`recommended_level`)で表示する**をデフォルトに(2026-08-14 決定)。
   共通Levelで揃える現在の挙動も、モード切替として残す価値はある(仕様策定で判断)。

### 🔴 B. `.klog`(実測)が読めない — 公開価値の本体

`src/` に `klog` の文字列が1つもない。設計カーブしか描けない。

**この記録プロジェクトの方法論の核心は「設計 vs 実測」である。**
記事08 は「設計どおりに動かなかったことを温度基準で発見した回」だった。
実測を重ねられないツールでは、その話ができない。

英語圏のフォーラムにも `.klog` を貼って読み方を尋ねるスレッドがある
(community.kaffelogic.com viewtopic t=368)。
**設計と実測を重ねられるツールは、まだ誰も出していない可能性が高い。**

### C. 公開の前提が未整備

- `package.json` が `"private": true`
- LICENSE なし
- UI が日本語のみ(主要ユーザーは英語圏)
- ホスティング先未定

## 🎯 差別化の核: 温度基準アラインメント

**これは他のどのツールにもない。実装すれば決定的な差別化になる。**

1ハゼは自動検出ではなく**ユーザーがボタンを押した時刻**が記録される。
豆の弾け方が変わると押す位置がずれ、メイラードと発展相の配分が
実態と違って記録される。

実例(log0032 vs log0033):

| | ボタン基準 | 温度基準(202.2℃通過) |
|---|---|---|
| log0033 発展相 | 72.8s(−11.7s) | **86.4s(+1.9s)** |
| log0033 メイラード | 236s(+40s) | **222s(+26s)** |

**ボタン基準では「発展相が縮んだ」と読めるが、実際は縮んでいなかった。**

→ **複数の実測ログを「指定温度の通過時刻」で揃え直して重ねる機能**。
   フェーズ比較を客観的にする。出典: `Profiles/_klog/log0033.md` 本文の訂正セクション。

## `.klog` フォーマット(実測で確認済み・2026-08-14)

仕様策定・実装セッションはこれを前提にしてよい。**再調査は不要。**

```
プレーン ASCII / LF。前半は key:value のヘッダ、後半がタブ区切りのデータ行。
```

### イベント行(`!` 始まり)

| キー | 内容 |
|---|---|
| `!first_crack` | 1ハゼの秒数。**ユーザーの手押し** |
| `!roast_end` | 焙煎終了の秒数 |
| `!development_percent` | DTR% |
| `!roast_end_reason` | 終了理由 |
| `!anti_beanlock` / `!motor_supply_noise` | その他 |

### データ行(タブ区切り・14列)

空文字を除いた 0-indexed で:

| index | 内容 |
|---|---|
| 0 | 時間(秒) |
| 1 | `spot_temp` — 生のセンサー値。ノイズ大 |
| 2 | `temp` — **焙煎終了のトリガーはこれ** |
| 3 | `mean_temp` — 平滑化された豆温度。**`end_temp_mean_c` はこれの終了時点値** |
| 4〜13 | ファン回転数・電力など(要確認) |

⚠️ 先頭に `offsets` 行など、数値に変換できない行が混ざる。`float()` で弾く。

### 既存の解析結果

`Profiles/_klog/logNNNN.md` に frontmatter として解析済みの値がある
(`first_crack_mmss` / `dtr_s` / `development_pct` / `end_temp_mean_c` 等)。
**実装の検算に使える。**

⚠️ ただし frontmatter は**ボタン基準**。温度基準の訂正は `.md` の**本文**にしかない。

## セッション分割

### Session 1: 仕様策定(**Opus**)

**なぜ Opus か**: 判断の比重が高く、出力量は少ない。
「他人が何を必要とするか」「名前をどうするか」「何を作らないか」は
コード量ではなく判断の質で決まる。

**やること**

1. **英語圏コミュニティの要件調査**
   - community.kaffelogic.com / kl-profiles.com を読み、
     ユーザーが実際に困っていること・欲しがっているものを拾う
   - 「最低限必要なもの」を推測でなく**観測から**決める
2. **アプリ名の再検討**
   - `.klog` も扱うので `kpro-diff` は実態と合わなくなる
   - 判断基準: 検索されるか / Kaffelogic ユーザーに意味が通るか /
     ドメインが取れるか / Kaffelogic の商標を侵さないか
3. **機能の優先順位づけ**(全部作らない。公開に必要な最小を決める)
4. **`docs/SPEC.md` を書く** — 実装セッションが判断せずに済む粒度で
   - 各機能の**受け入れ条件**(何が表示されれば完成か)
   - 検算に使う具体値(例: log0033 の温度基準 発展相 86.4s)
   - UI の構成(どこに何を置くか)
5. **やらないことリスト** — 実装セッションの暴走を防ぐ

**成果物**: `docs/SPEC.md` / 名前の決定 / 実装の順序

**開始プロンプト**

```
~/00.PJ/Kaffelogic/kpro-diff/docs/PLAN.md を読んで、Session 1(仕様策定)をお願いします。

現状のアプリは http://localhost:5173 で動いています(dev サーバー起動済み)。
実際に .kpro を読ませて挙動を確認してから仕様を書いてください。
サンプルは ~/Obsidian/brain/Projects/Kaffelogic焙煎修行/Profiles/_kpro/ に27本、
実測ログは同 _klog/ に35本あります。

成果物は docs/SPEC.md です。実装はしないでください。
```

### Session 2: 実装(**Sonnet 5**)

**なぜ Sonnet か**: SPEC が固まっていれば、TypeScript/React の実装は
判断より作業量の勝負になる。受け入れ条件が明文化されていれば品質は落ちない。

**前提**: `docs/SPEC.md` が存在すること。**なければ Session 1 に戻る。**

**やること**

- SPEC のとおりに実装する
- **仕様の判断が必要になったら、勝手に決めずに止めて聞く**
- 1機能ごとにコミット
- 各機能の受け入れ条件を、実際にブラウザで確認してから完了とする

**開始プロンプト**

```
~/00.PJ/Kaffelogic/kpro-diff/docs/SPEC.md を読んで実装してください。

dev サーバーは http://localhost:5173 で起動済みです。
実装したら必ずブラウザで表示を確認し、SPEC の受け入れ条件を満たすか検証してください。
サンプルは ~/Obsidian/brain/Projects/Kaffelogic焙煎修行/Profiles/_kpro/ と _klog/ にあります。

SPEC に書かれていない判断が必要になったら、実装せずに質問してください。
1機能ごとにコミットしてください。
```
